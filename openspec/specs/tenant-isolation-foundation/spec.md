# tenant-isolation-foundation Specification

## Purpose
定义多租户平台的核心隔离模型、请求租户上下文与租户初始化基础能力，确保数据、身份和配置在平台内按租户严格收口。
## Requirements
### Requirement: 所有核心对象具备显式租户归属
系统 SHALL 为身份、组织、权限、业务数据、配置和审计等核心对象建立显式租户归属，并保证每个对象只属于一个租户。任何跨租户共享对象 MUST 以平台级显式语义建模，而不是隐式复用租户对象。

#### Scenario: 创建租户内业务对象
- **WHEN** 用户在某个租户上下文中创建员工、客户、合同或流程模板
- **THEN** 系统为该对象绑定当前租户归属，并在后续访问中保持租户一致性

#### Scenario: 平台级对象与租户对象区分建模
- **WHEN** 平台运营者维护平台默认模板或平台级配置
- **THEN** 系统将其识别为平台级对象，而不是错误落入某个租户内部对象集合

### Requirement: 会话与请求强制遵守租户边界
系统 SHALL 让登录会话、刷新会话、API 凭证和所有受保护请求都绑定租户上下文，并在鉴权与数据访问阶段强制应用租户边界。请求 MUST NOT 读取或修改不属于当前租户的数据。

#### Scenario: 租户用户访问本租户数据
- **WHEN** 一个租户用户携带有效会话访问受保护接口
- **THEN** 系统仅允许其访问当前租户内的数据和配置

#### Scenario: 请求试图跨租户访问数据
- **WHEN** 用户或 API 凭证尝试访问其他租户的数据
- **THEN** 系统拒绝该请求，并保留对应的安全审计记录

### Requirement: 新租户具备可初始化的默认基础能力
系统 SHALL 支持为新租户执行初始化流程，自动创建基础组织、默认角色、权限目录、种子模板和基础配置，使新租户能够在开通后快速进入可用状态。

#### Scenario: 平台创建新租户
- **WHEN** 平台运营者创建一个新租户
- **THEN** 系统完成该租户的基础初始化，并生成默认治理与使用入口

#### Scenario: 初始化失败可被追踪
- **WHEN** 新租户初始化过程中出现失败
- **THEN** 系统记录失败步骤和上下文，并允许平台运营者定位和重试

### Requirement: OA、流程与开放平台更新链路在数据访问层强制租户约束
系统 SHALL 让 OA 申请、流程模板与实例、开放平台凭证、Webhook 和身份连接器的核心读写在数据访问层强制应用当前租户约束，而不是只依赖上层服务在进入前手工断言。任何带租户归属的更新操作 MUST 同时校验对象标识与租户标识。

#### Scenario: 创建 OA 或流程对象时写入当前租户
- **WHEN** 当前租户用户创建请假申请、行政申请、流程模板或流程实例
- **THEN** 系统在持久化时为这些对象写入当前租户标识，并在后续读取中继续使用该租户标识过滤

#### Scenario: 更新租户级开放平台对象时同时校验对象与租户
- **WHEN** 某个租户用户更新 API 凭证、Webhook 订阅或身份连接器
- **THEN** 系统在数据访问层同时校验对象标识和当前租户标识，不允许仅按主键执行更新

### Requirement: 跨租户候选人解析与目录查询不得落到全局空间
系统 SHALL 让审批人解析、流程审批人解析、公告查询和通讯录查询在候选对象解析阶段即绑定当前租户。任何“按权限找人”或“按状态找部门”能力 MUST NOT 跨租户扫描全局数据。

#### Scenario: OA 默认审批人在租户内解析
- **WHEN** OA 申请人在当前租户内发起申请并需要系统解析默认审批人
- **THEN** 系统仅在该租户内查找具备对应权限的审批人，而不会命中其他租户员工

#### Scenario: 工作流节点审批人在租户内解析
- **WHEN** 流程模板节点按用户集合或权限目录解析审批人
- **THEN** 系统仅返回当前租户内且满足条件的员工集合
