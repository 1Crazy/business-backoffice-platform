# backoffice-super-app-shell Specification

## Purpose
定义统一前端主应用壳层在多后台子域场景下的入口职责、导航结构、子应用挂载规则与宿主/子应用运行边界，确保 OA、SCRM 及后续新增子域能够在同一工作台中被一致承载。
## Requirements
### Requirement: 主应用提供统一入口与跨域导航壳层
系统 SHALL 提供一个统一前端主应用，作为 `platform`、OA 与 SCRM 等后台子域的默认入口。主应用 MUST 提供统一登录页、全局导航壳层、页面标题区、权限兜底页面与内容挂载容器，使用户无需在多个独立站点之间自行判断入口。

#### Scenario: 用户登录后进入首个可访问的业务页面
- **WHEN** 用户在主应用完成登录并具备至少一个平台治理、OA 或 SCRM 页面权限
- **THEN** 系统将其导向该用户第一个可访问的主应用菜单页面，而不是停留在空白首页或要求手工再选择子系统

#### Scenario: 主应用统一展示平台治理、OA 与 SCRM 菜单
- **WHEN** 用户进入主应用壳层并拥有平台治理、OA、SCRM 之一或多个域的页面权限
- **THEN** 系统在同一导航结构中展示按业务域分组的菜单入口，并只显示当前用户有权限访问的页面

### Requirement: 主应用同时承载平台原生页面与业务子应用
统一主应用 SHALL 同时支持两类内容承载方式：一类是通过 `qiankun` 挂载的 OA 与 SCRM 业务子应用，另一类是主应用原生承载的平台治理页面。平台治理页面 MUST 位于 `/platform/**` 路由空间下，并在不依赖额外业务子应用的前提下完成渲染。

#### Scenario: 主应用进入平台治理页面时渲染原生内容
- **WHEN** 用户在主应用中访问 `/platform/organization/departments`、`/platform/organization/employees` 或其他 `/platform/**` 页面
- **THEN** 主应用直接渲染对应的平台治理页面，而不是要求额外挂载 OA 或 SCRM 子应用

#### Scenario: 主应用进入业务域页面时继续激活子应用
- **WHEN** 用户在主应用中访问 `/oa/**` 或 `/scrm/**` 页面
- **THEN** 系统继续按现有规则激活对应业务子应用，而不会因为平台治理域的引入改变 OA 与 SCRM 的承载方式

### Requirement: 主应用通过 qiankun 承载 OA 与 SCRM 内容页
主应用 SHALL 使用 `qiankun` 承载 `oa-web` 与 `scrm-web` 子应用，并根据当前路由前缀激活相应子应用。OA 页面 MUST 挂载在 `/oa/**` 路径空间下，SCRM 页面 MUST 挂载在 `/scrm/**` 路径空间下。

#### Scenario: 主应用进入 OA 页面时激活 OA 子应用
- **WHEN** 用户在主应用中访问 `/oa/workspace` 或其他 `/oa/**` 页面
- **THEN** 系统加载并激活 `oa-web` 子应用，在主应用内容区渲染对应 OA 页面

#### Scenario: 主应用进入 SCRM 页面时激活 SCRM 子应用
- **WHEN** 用户在主应用中访问 `/scrm/dashboard` 或其他 `/scrm/**` 页面
- **THEN** 系统加载并激活 `scrm-web` 子应用，在主应用内容区渲染对应 SCRM 页面

### Requirement: 子应用在宿主模式与独立模式下都可运行
`oa-web` 与 `scrm-web` SHALL 同时支持独立运行模式与 `qiankun` 宿主模式。子应用在独立运行时 MUST 保留完整登录与导航壳层；在宿主模式下 MUST 隐藏重复的应用级导航壳层，仅渲染业务内容区，并继续保持原有页面权限、路由守卫与业务行为。

#### Scenario: 子应用独立运行时保留原有体验
- **WHEN** 开发者直接启动 `oa-web` 或 `scrm-web` 并单独访问其本地地址
- **THEN** 子应用继续展示自己的登录页、导航壳层和业务页面，不依赖主应用存在

#### Scenario: 子应用被主应用承载时只渲染业务内容
- **WHEN** `oa-web` 或 `scrm-web` 通过 `qiankun` 被挂载到主应用容器中
- **THEN** 子应用隐藏自身重复的侧边栏、移动导航和顶部壳层，并在不改变业务页面行为的前提下输出内容区

### Requirement: 主应用壳层持续表达当前业务域上下文
主应用 SHALL 在统一门户壳层中持续表达当前业务域上下文。当前激活业务域的导航分组 MUST 保持可辨识，并且页面标题区 MUST 在不依赖子应用自身导航壳层的情况下继续提供当前页面与统一身份上下文。

#### Scenario: 用户进入平台治理页面时当前域分组保持可辨识
- **WHEN** 用户在主应用中进入任意 `/platform/**` 页面
- **THEN** 主应用导航保持 `platform` 分组为当前上下文，并让用户能够从壳层中直接辨认自己正在平台治理域内工作

#### Scenario: 用户进入 SCRM 页面时当前域分组保持可辨识
- **WHEN** 用户在主应用中进入任意 `/scrm/**` 页面
- **THEN** 主应用导航保持 `scrm` 分组为当前上下文，并让用户能够从壳层中直接辨认自己正在 SCRM 域内工作

#### Scenario: 用户进入 OA 页面时当前域分组保持可辨识
- **WHEN** 用户在主应用中进入任意 `/oa/**` 页面
- **THEN** 主应用导航保持 `oa` 分组为当前上下文，并让用户能够从壳层中直接辨认自己正在 OA 域内工作

### Requirement: 主应用导航分组以业务语义标签为主文案
主应用 SHALL 使用业务语义标签作为导航父级分组的主文案。桌面侧边导航中的 OA 与 SCRM 分组 MUST 直接展示诸如“协同事务”“经营管理”之类的业务名称，而不是在主文案前额外叠加 `OA`、`S` 等域前缀徽标。

#### Scenario: 桌面侧边导航直接显示业务分组名称
- **WHEN** 用户在桌面宽度进入主应用并看到父级导航分组
- **THEN** 分组主文案直接显示业务语义标签，且不会在标题前额外出现 `OA`、`S` 等域前缀徽标

### Requirement: 主应用宿主内容区不得为嵌入态子应用制造空滚动
主应用 SHALL 让微应用挂载容器继承宿主内容区的可用高度，并约束 `qiankun` 注入的包装层与子应用根节点在宿主模式下保持自然高度。若嵌入态子应用内容本身未超出宿主内容区，一层额外的宿主纵向滚动 MUST NOT 出现。

#### Scenario: OA 页面在一屏内时宿主内容区不出现空滚动
- **WHEN** 用户在主应用中访问一屏内可容纳的 `/oa/**` 页面
- **THEN** 主应用内容区不会因为微应用包装层或嵌入态根节点被拉伸而额外出现一层纵向滚动条

#### Scenario: 子应用内容真实超出时仍允许宿主滚动
- **WHEN** 用户在主应用中访问内容本身超过当前内容区高度的 `/scrm/**` 或 `/oa/**` 页面
- **THEN** 主应用内容区仍允许真实的纵向滚动，以保证超出部分可以被访问

### Requirement: 主应用宿主模式不得裁切子应用业务弹层
当 `oa-web` 或 `scrm-web` 被主应用承载时，主应用宿主容器 SHALL 允许子应用对话框、抽屉和其他覆盖层完整显示。宿主滚动容器和布局壳层 MUST NOT 让这些业务弹层被裁切、遮挡或只能在不可见区域渲染。

#### Scenario: SCRM 页面打开对话框时不被宿主内容区裁切
- **WHEN** 用户在主应用中打开 SCRM 页面里的新增、编辑、分配或收口对话框
- **THEN** 对话框完整显示在当前视口层级之上，而不是被宿主内容区边界裁切

#### Scenario: SCRM 页面打开抽屉时不被宿主内容区裁切
- **WHEN** 用户在主应用中打开 SCRM 页面里的详情或跟进抽屉
- **THEN** 抽屉完整显示并可正常滚动、关闭与操作，而不是被宿主内容区遮挡

### Requirement: 主系统原生平台页与嵌入态子应用保持连续的壳层阅读节奏
主应用 SHALL 在统一宿主壳层中同时承托原生平台页与嵌入态子应用时，保持连续的视觉阅读节奏。用户从 `/platform/**` 切换到 `/oa/**` 或 `/scrm/**` 时，顶部标题区、侧边导航和原生页的结构化组件反馈 MUST 维持宿主级连续性，而不是让原生平台页看起来像独立于统一工作台之外的另一套产品。

#### Scenario: 从平台治理页切换到子应用页时宿主观感连续
- **WHEN** 用户从主系统平台治理页切换到宿主承载的 OA 或 SCRM 页面
- **THEN** 主系统侧边导航、顶部标题区与内容容器保持连续的门户节奏，用户不会因为原生页签、卡片或表格反馈突变而感到主系统和子系统是彼此割裂的两套后台

#### Scenario: 原生平台页在宿主内保持统一工作台身份
- **WHEN** 用户进入 `/platform/organization/departments`、`/platform/organization/employees` 或其他主系统原生页面
- **THEN** 页面通过与宿主壳层一致的结构节奏和主题覆盖持续表达“统一工作台中的平台治理域”身份，而不是呈现成与宿主导航脱节的独立页面皮肤

### Requirement: 宿主与子应用的样式边界在切换过程中保持稳定
主应用 SHALL 在承载 `oa-web` 与 `scrm-web` 时保持稳定的样式边界。宿主原生页面样式、OA 样式与 SCRM 样式 MUST 在各自生效范围内独立运作，用户来回切换业务域时不得因为遗留样式或全局覆盖顺序变化而看到宿主或子应用样式错位。

#### Scenario: 宿主切回原生平台页后维持自己的组件样式
- **WHEN** 用户从 `/oa/**` 或 `/scrm/**` 页面返回 `/platform/**` 页面
- **THEN** 宿主原生页面仍然呈现主系统定义的组件样式和宿主主题，不会因为子应用卸载后的样式残留而发生 tab、按钮、输入框或表格反馈变化

#### Scenario: 宿主切换业务域时当前子应用只呈现自身主题
- **WHEN** 用户在主系统内从 OA 页面切换到 SCRM 页面，或从 SCRM 页面切换到 OA 页面
- **THEN** 当前业务域只呈现自身主题与组件皮肤，不会出现另一个子应用遗留样式继续影响当前页面的情况
