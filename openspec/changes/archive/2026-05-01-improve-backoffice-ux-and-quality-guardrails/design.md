## Context

当前主应用通过 `apps/main-web/src/config/navigation.ts` 维护宿主导航，OA/SCRM 子应用又从各自 router 动态生成菜单。虽然上一阶段已经对齐过部分权限键，但结构上仍然是三套来源。布局层也存在重复实现：主应用、OA 和 SCRM 都隐藏内容区滚动条，并分别维护嵌入态样式。

微前端运行时目前保留 qiankun 默认 sandbox，并在注释中说明更强样式隔离会导致白屏。这个选择能保证链路可用，但样式串扰和嵌入态布局漂移风险仍在。开放平台的 Webhook 测试投递则通过 URL 字符串中的 `fail` / `retry-once` 模拟结果，用户看到的状态不能代表真实外部端点是否可达。

## Goals / Non-Goals

**Goals:**
- 降低主应用与子应用菜单、权限、路由标题和可见性的漂移概率。
- 让后台页面在宿主模式、独立模式、桌面和移动端都有可发现滚动和稳定布局。
- 让微前端加载失败、样式隔离和嵌入态错误有可诊断表现。
- 让 Webhook 测试结果具备真实语义，避免模拟结果被误当作真实投递。
- 给关键后端模块和主要前端壳层补齐最小测试/截图验证。

**Non-Goals:**
- 不重做视觉品牌或大规模改版。
- 不替换 qiankun 或重写微前端架构。
- 不把所有页面都改造成新组件体系。
- 不在本 change 中引入完整 E2E 测试平台。

## Decisions

### 1. 页面契约集中定义，子应用消费契约

主应用应继续作为跨域导航入口，但 OA/SCRM 需要消费同一份页面契约或生成校验快照，避免重复维护 title、permission、path、hidden 等字段。短期可新增共享契约测试，长期可抽出 workspace 内部共享模块。

验收标准：任一宿主导航项对应的子应用路由权限不一致时，测试失败。

### 2. 后台滚动条保持可发现但不过度打扰

内容区不能全局隐藏滚动条。桌面端应保留细滚动条或在滚动容器边缘提供明确视觉反馈；移动端保留原生滚动体验。表格、抽屉、长表单等固定格式区域需要稳定高度和溢出策略。

验收标准：长列表、长表单和嵌入子应用页面在桌面和移动端都能直观看出可滚动，且内容不被顶栏或底部遮挡。

### 3. 微前端隔离以可验证策略推进

不直接一次性打开 qiankun 实验性隔离。先建立视觉回归检查和错误态诊断，再逐步收敛样式作用域、overlay 容器、Element Plus 弹层挂载和嵌入态全局 CSS。若再次尝试样式隔离，必须有截图/像素检查证明非白屏。

验收标准：OA/SCRM 在 host 和 standalone 两种模式下弹层、选择器、表格、移动导航表现一致。

### 4. Webhook 测试必须区分真实与模拟

当前字符串模拟不应继续被展示成真实投递。如果短期无法真发 HTTP 请求，UI 和 API 字段必须明确返回 `simulation` 类型；更理想的实现是服务端执行真实 POST，限制协议、内网地址、超时、重定向和响应体长度，避免 SSRF。

验收标准：用户能明确区分模拟检查和真实投递；真实投递失败时显示真实状态码、错误原因和耗时。

### 5. 测试护栏按风险优先

后端优先补认证、开放集成、上传、租户边界测试；前端优先补宿主导航契约、登录失效跳转、微前端加载失败态和移动端菜单。测试不追求大而全，先覆盖最容易回归的边界。

验收标准：`pnpm -r test` 至少覆盖新增关键测试；无法自动化的视觉检查必须记录手动验证步骤。

## Risks / Trade-offs

- [Risk] 抽共享导航契约可能影响三个前端包的构建边界。Mitigation: 先用测试校验重复配置，再视复杂度决定是否抽共享模块。
- [Risk] 恢复滚动条会改变既有视觉观感。Mitigation: 使用细滚动条与局部容器策略，避免页面突然变得粗糙。
- [Risk] 真实 Webhook 投递会引入 SSRF 风险。Mitigation: 必须先做 URL allow/block 规则、内网地址拦截、超时和响应体裁剪。
- [Risk] 视觉验证成本上升。Mitigation: 只覆盖壳层、嵌入态和高频页面，不对所有业务页截图。
