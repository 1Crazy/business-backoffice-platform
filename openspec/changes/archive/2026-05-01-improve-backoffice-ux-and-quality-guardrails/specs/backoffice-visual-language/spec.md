## MODIFIED Requirements

### Requirement: 视觉升级遵循响应式与可访问性基线
系统 SHALL 在视觉升级中内建响应式与可访问性基线，包括桌面与移动端断点适配、可见焦点态、键盘可达性、足够的文字对比度与 reduced-motion 支持。装饰性动效 MUST NOT 成为信息理解或核心操作的前置条件。后台长列表、长表格、长表单和嵌入态内容区 MUST 提供可发现的滚动反馈，不得让用户只能通过猜测判断内容是否可继续滚动。

#### Scenario: 窄屏下保持可读与可操作
- **WHEN** 用户在平板或移动宽度下访问登录页、首页或二级页面
- **THEN** 导航、标题、卡片、筛选与按钮按照窄屏布局重排，且核心信息不依赖横向滚动才能理解

#### Scenario: 减少动态效果用户仍可完成操作
- **WHEN** 用户系统偏好启用了减少动态效果
- **THEN** 后台应用降低或关闭非必要动效，同时保留完整的信息可见性与交互可用性

#### Scenario: 长内容区域提供可发现滚动反馈
- **WHEN** 用户访问超过当前视口高度的表格、表单、抽屉或嵌入态子应用页面
- **THEN** 页面提供可发现的滚动反馈
- **AND** 重要内容不会被顶部栏、底部边界或宿主容器遮挡

### Requirement: 多后台应用的全局组件皮肤不得跨应用边界串扰
系统 SHALL 约束 `main-web`、`oa-web` 与 `scrm-web` 的全局组件皮肤作用域。任一应用对 `Element Plus` 基础结构的视觉覆盖 MUST 限制在自身宿主语境内，不得在用户切换平台原生页、OA 与 SCRM 时继续污染其他应用的 tab、按钮、表格、输入框或卡片样式。宿主与子应用的嵌入态布局 MUST 通过可验证视觉检查确认非白屏、非错位、非横向溢出。

#### Scenario: 子应用切换后不会污染主系统原生页签
- **WHEN** 用户在主系统内访问 OA 或 SCRM 页面后再返回 `main-web` 原生平台页
- **THEN** 主系统原生页签、按钮、表格和卡片继续使用主系统定义的视觉结构，不会被子应用遗留的全局组件样式覆盖

#### Scenario: 一个子应用不会覆盖另一个子应用的组件皮肤
- **WHEN** 用户在主系统内从 OA 页面切换到 SCRM 页面，或从 SCRM 页面切换到 OA 页面
- **THEN** 当前子应用只呈现自身主题下的组件皮肤，不会继承另一个子应用遗留的 tab、按钮、表格或输入框样式

#### Scenario: 嵌入态视觉验证覆盖主要断点
- **WHEN** 团队修改宿主壳层、微前端容器或子应用全局样式
- **THEN** 验证流程覆盖桌面和移动端的 host 嵌入 OA、host 嵌入 SCRM、standalone OA 与 standalone SCRM
- **AND** 结果证明页面非白屏、内容不重叠且无非预期横向溢出
