## Context

当前产品结构已经具备三块基础能力：`main-web` 统一入口、`oa-web` 办公协同域、`scrm-web` 经营管理域。与此同时，组织、员工、角色和权限目录已经演进成共享平台能力：同一员工身份可以进入多个后台应用，权限目录也已经具备应用命名空间。

但现有前端信息架构仍保留明显的历史残留。`apps/main-web/src/config/navigation.ts` 仍把“部门管理”放在 SCRM 分组下，`apps/scrm-web` 中的 `AccessControlPage` 同时承载部门、员工和角色管理页面，而对应的权限种子仍使用 `appCode = "scrm"`。这让“平台治理能力”在产品层、导航层和权限目录层都继续被误读成 SCRM 私有模块。

这次 change 的核心不是简单换一个菜单名字，而是把长期结构一次性定对：

- OA 继续承载员工日常协同与流程办公。
- SCRM 继续承载客户、线索、商机与经营分析。
- 平台治理独立成为第三个产品域，专门承载组织、员工、角色、授权、会话与审计这类跨业务共享治理能力。

## Goals / Non-Goals

**Goals:**

- 在统一主应用中引入 `platform` 作为与 `oa`、`scrm` 并列的长期业务域。
- 把组织、员工、角色与授权治理的产品归属从 SCRM 页面提升为平台级治理能力。
- 为平台治理域定义清晰的信息架构、导航语义和路由前缀，例如 `/platform/**`。
- 让角色授权目录可以自然表达 `platform`、`oa`、`scrm` 三类权限归属，而不是继续把治理权限挂在 `scrm` 下。
- 设计一条低风险迁移路径，允许先复用现有组织/员工/角色实现，再逐步完成页面拆分和命名收敛。

**Non-Goals:**

- 不在本次 change 中新增完整的会话治理、审计日志、安全策略等全部平台治理页面。
- 不在本次 change 中立即拆分独立的 `platform-web` 微前端应用。
- 不在本次 change 中重写组织、员工、角色的后端领域模型或 CRUD 基础能力。
- 不把 OA 的组织通讯录改造成治理后台；通讯录仍然保留为 OA 只读办公入口。
- 不要求首个实现阶段就把“部门、员工、角色”拆成完全独立的前端工程模块，只要求对外产品结构先收口正确。

## Decisions

### 1. 引入 `platform` 作为与 OA、SCRM 并列的顶层产品域

Decision:
统一主应用新增 `platform` 顶层业务域，用于承载组织、员工、角色、授权以及后续安全治理能力。它在导航、页面标题、域上下文和路由空间上都与 `oa`、`scrm` 并列，而不是作为 SCRM 或 OA 的子菜单存在。

Rationale:

- 组织、员工、角色和授权天然服务多个业务域，继续挂在任何一个业务域下面都会产生错误心智。
- 当前仓库已经具备统一主应用壳层，不需要再依靠“某个业务系统代管共享能力”。
- 先把产品域划分清楚，后续新增第三个业务前端时可以直接套用这一结构。

Alternatives considered:

- 继续放在 `scrm-web`：改动最小，但会持续强化“平台治理等于 SCRM 配置页”的错误语义。
- 转移到 `oa-web`：会破坏 OA 的办公协同心智，并让治理后台看起来像 OA 附属功能。

### 2. 平台治理首期由 `main-web` 原生承载，而不是立刻新增 `platform-web`

Decision:
`/platform/**` 页面首期由 `main-web` 原生路由和页面壳层承载。OA 与 SCRM 继续作为 `qiankun` 子应用存在；平台治理则作为统一壳层内的原生域页面存在，后续只有在规模和团队边界足够明确时才考虑拆出 `platform-web`。

Rationale:

- `main-web` 已经是最中性的入口层，适合优先承接平台原生能力。
- 平台治理域当前页面数量有限，立刻增加第三个微前端应用会引入额外运行时和开发复杂度，但不会显著提升当前价值。
- 原生承载可以更快完成语义纠偏，同时保留后续拆分空间。

Alternatives considered:

- 立即新增 `platform-web`：长期可能成立，但当前会过早引入第三个前端应用的工作流、构建和接入成本。
- 继续沿用 `scrm-web` 页面并只改文案：实现便宜，但无法真正完成产品边界迁移。

### 3. 平台治理采用中性路由空间，并按“组织 / 授权 / 安全”分层扩展

Decision:
平台治理统一使用 `/platform/**` 路由空间。首批信息架构至少覆盖：

- `/platform/organization/departments`
- `/platform/organization/employees`
- `/platform/access/roles`

后续可在同一域下继续扩展：

- `/platform/security/sessions`
- `/platform/audit/logs`

首期实现允许底层复用现有 `AccessControlPage` 的数据编排和展示组件，但对外导航、页面标题、面包屑和路由语义必须以平台治理域为准。

Rationale:

- 中性路由空间可以直接表达“这是平台治理，而不是业务域页面”。
- 先按治理主题拆分信息架构，比继续保留一个名叫“部门管理”却同时塞着员工和角色的聚合页更符合长期维护。
- 即使首期实现仍复用旧组件，对外产品结构也能先稳定下来。

Alternatives considered:

- 只保留 `/platform/access-control` 单页：短期简单，但会继续延续旧信息架构，不利于后续扩展会话和审计模块。
- 完全重做所有页面后再迁移：结构更完整，但交付路径过长，不利于先完成语义收口。

### 4. 治理权限的应用归属从 `scrm` 迁移到 `platform`

Decision:
权限目录中与组织、员工、角色和治理后台访问相关的权限项，应用归属应迁移到 `platform`。现有权限 code 如 `department:read`、`user:write`、`role:read` 可以首期保持不变，以降低接口和路由改造成本；但角色授权目录、导航归属和权限说明都必须把它们视为平台治理权限，而不是 SCRM 权限。

Rationale:

- 当前权限目录虽然支持 `appCode`，但治理权限仍标在 `scrm` 下，和长期产品结构相冲突。
- 保持 code 稳定、迁移 appCode，可以在不大规模破坏接口契约的前提下完成语义纠偏。
- 这样角色编辑页可以自然分出 `platform`、`oa`、`scrm` 三组权限。

Alternatives considered:

- 连同 permission code 一起改为 `platform:*`：语义更纯粹，但会带来更大范围的前后端兼容改造。
- 保持 `appCode = scrm` 只改菜单位置：会让权限目录和实际产品结构持续不一致。

### 5. 迁移采取“语义先行、实现渐进”的分阶段策略

Decision:
迁移按以下顺序推进：

1. 先更新 OpenSpec，明确平台治理域、导航归属与权限归属。
2. 在 `main-web` 中新增平台治理导航与路由空间。
3. 调整治理权限的 `appCode` 与角色授权分组。
4. 为旧的 `/scrm/departments` 等入口提供跳转或兼容别名，避免已有链接立即失效。
5. 再逐步把现有聚合页拆成更符合长期结构的组织、员工、角色等页面入口。

Rationale:

- 先定语义和 IA，可以避免后续实现一边做一边重新争论归属。
- 兼容旧入口能够降低联调期和迁移期的使用风险。
- 渐进拆分可以复用现有组织/员工/角色能力，避免为了“结构正确”而一次性推倒重来。

Alternatives considered:

- 一次性删除旧入口并全量迁移：结构最干净，但回归面过大。
- 永久保留旧 `scrm` 入口：会让新旧语义长期并存，难以真正完成迁移。

## Risks / Trade-offs

- [Risk] 现有用户可能已经把治理后台理解为 SCRM 一部分，迁移后会产生短期认知成本。 -> Mitigation: 在平台治理域首期保持熟悉的表单与表格交互，并提供旧入口跳转和明确的导航文案。
- [Risk] 治理权限的 `appCode` 从 `scrm` 迁到 `platform` 会波及 seed、角色授权分组和部分测试。 -> Mitigation: 首期保持 permission code 不变，只迁移归属字段和展示逻辑，降低改动半径。
- [Risk] `main-web` 同时承载原生平台页面与 `qiankun` 子应用，会让壳层实现复杂度上升。 -> Mitigation: 把平台原生页面约束在独立路由段与独立 layout/context 适配层中，避免反向耦合到 OA/SCRM 子应用。
- [Risk] 如果首期仍复用旧 `AccessControlPage` 聚合实现，产品结构和页面内部结构会短期不完全一致。 -> Mitigation: 在设计中明确这是可接受的中间态，并把页面拆分列入后续任务。

## Migration Plan

- 第一步：新增 `platform-governance-workspace` spec，并更新 `access-control`、`backoffice-super-app-shell` 的行为约束。
- 第二步：在 `main-web` 中引入 `platform` 域导航与 `/platform/**` 路由空间，完成产品级 IA 迁移。
- 第三步：把组织、员工、角色相关权限的 `appCode` 从 `scrm` 调整为 `platform`，同步角色授权目录分组与权限文案。
- 第四步：为旧的 SCRM 治理入口提供跳转或兼容别名，确保历史访问路径不会立即失效。
- 第五步：逐步将现有治理页面从“聚合页 + 页签”演进为更符合平台治理 IA 的入口组织。

Rollback strategy:

- 若平台导航迁移在上线期引发问题，可暂时保留旧 SCRM 入口并回退主导航显示，但不回退已补充的 spec 定义。
- 若权限归属迁移影响角色授权，可临时双写兼容 `scrm` 与 `platform` 分组展示，待数据校正后再收敛。

## Open Questions

- 平台治理域首期对外文案使用“平台治理”还是“组织与权限中心”更利于用户理解。
- 首次落地时是否就把“部门、员工、角色”做成三个独立页面入口，还是先以平台域下的聚合页作为过渡态。
- 会话治理与审计日志是作为首批可见菜单一起推出，还是只在 IA 中预留扩展位置，后续单独立项实现。
