## Context

仓库当前已经有两个可独立运行的 Vue 前端应用：

- `apps/oa-web`：面向办公协作流程，包含 OA 工作台、审批中心、请假申请、公告通知与组织通讯录。
- `apps/scrm-web`：面向销售运营流程，包含看板、客户、线索、商机、权限治理与系统管理。

这两个应用已经共享统一的会话 key、登录接口和当前用户资料接口，因此账号体系本身已经具备“平台级统一身份”的基础；但它们的前端入口、导航壳层和页面标题仍然各自独立，导致用户需要在多个后台之间自行切换。

用户已经明确选择 `qiankun` 作为集成方案，并强调代码需要易于维护。因此本次设计的重点不是“尽快把两个站点嵌进来”，而是建立一套足够清晰的宿主/子应用边界，让主应用负责统一壳层，而业务页面仍然留在各自子应用内部演进。

## Goals / Non-Goals

**Goals:**

- 新增 `apps/main-web` 作为统一主应用，承载登录页、全局导航、页面标题区和子应用挂载容器。
- 使用 `qiankun` 将 `oa-web` 与 `scrm-web` 接入主应用，并通过统一路由前缀承载其页面内容。
- 让主应用统一接管菜单信息架构，子应用在被承载时隐藏重复导航壳层，只保留内容区。
- 保留 `oa-web` 与 `scrm-web` 的独立运行能力，方便领域开发、单应用调试和问题隔离。
- 使用语义化样式令牌和集中式微前端运行时模块提升可维护性，避免将 `qiankun` 特判散落到页面和组件中。

**Non-Goals:**

- 不在本次 change 中引入新的后端聚合接口、BFF 或跨应用事件总线。
- 不在本次 change 中重写 OA 与 SCRM 现有业务页面实现，只做必要的宿主适配与壳层拆分。
- 不在本次 change 中抽离跨应用共享 UI 组件库；本次优先共享规范与运行模式，而不是共享实现。
- 不在本次 change 中支持多个子应用同时并屏显示；主应用仍以单内容区承载当前激活子应用。
- 不在本次 change 中处理第三方 SSO、跨标签协同或复杂的跨应用消息编排。

## Decisions

### 1. 新增 `apps/main-web` 作为唯一主应用壳层

Decision:
新增 `apps/main-web` 工作区，作为统一登录入口、导航壳层与 `qiankun` 宿主；`oa-web` 与 `scrm-web` 继续作为可独立运行的子应用保留。

Rationale:

- 这样可以把“壳层职责”和“业务页面职责”分离，避免在现有任一业务应用中强行混入集团级入口语义。
- 保留子应用独立运行能力后，领域团队仍然可以单独启动 OA 或 SCRM 进行开发与排障，不需要每次都依赖主应用联调。
- `main-web` 的存在也为未来接入第三个后台应用提供了稳定落点，而不必继续扩张某个业务应用本身。

Alternatives considered:

- 直接把 `scrm-web` 改造成主应用：改动看起来较小，但会让 SCRM 同时承担“业务应用”和“平台壳层”双重语义，长期难维护。
- 新建一个纯路由跳转门户而不真正承载子应用：无法满足“菜单内容页整合到同一个壳层里”的目标。

### 2. 使用 `qiankun` 的主应用注册模型承载两个 Vite 子应用

Decision:
主应用使用 `qiankun` 的 `registerMicroApps` / `start` 模式注册 `oa-web` 与 `scrm-web`，并通过 `/oa` 与 `/scrm` 前缀规则激活对应子应用。子应用继续保留各自的 Vite 工程，只在入口层补齐 `qiankun` 生命周期和运行模式兼容。

Rationale:

- `qiankun` 能让我们在不复制 OA/SCRM 页面代码的前提下，直接复用现有子应用的页面、路由和领域实现。
- 通过统一前缀激活子应用后，主应用路由和子应用路由的职责都很明确：主应用决定“当前进入哪个域”，子应用决定“该域内部的哪一个页面被展示”。
- 相比直接手工 iframe 嵌套，`qiankun` 能提供更自然的 DOM 承载、生命周期和样式隔离基础，后续扩展性更好。

Alternatives considered:

- 使用 iframe：实现更快，但样式、路由、加载态和宿主内交互会明显割裂。
- 直接把 OA/SCRM 页面复制进 `main-web`：短期可以得到“同一应用”体验，但会导致大规模重复代码和长期演进分叉。

### 3. 主应用统一接管菜单与页面标题，子应用在宿主模式下隐藏重复壳层

Decision:
主应用维护一份声明式菜单注册表，负责展示 OA / SCRM 分组、页面标题、副标题和权限兜底。`oa-web` 与 `scrm-web` 在 `qiankun` 宿主模式下隐藏各自的侧边栏、移动导航和顶部摘要区，仅保留业务内容容器；在独立运行模式下继续展示完整应用壳层。

Rationale:

- 这样能真正实现“菜单内容页整合进主应用”，而不是出现宿主一套菜单、子应用再套一套菜单的双层导航。
- 菜单配置集中在主应用后，后续新增页面或新增子应用时，维护点会稳定收敛到宿主侧配置，而不是散落在多个布局组件里。
- 子应用只需要感知“当前是否处于宿主模式”，而不需要知道宿主的完整视觉结构，领域边界更清晰。

Alternatives considered:

- 保留子应用原有侧边栏，仅由宿主提供一级入口：集成成本更低，但体验上仍然像两个系统嵌套，不符合用户目标。
- 让宿主动态读取子应用 router 配置：理论上更自动，但会把宿主强绑定到子应用内部实现，不利于维护。

### 4. 鉴权继续复用平台级会话存储，并用集中式运行时模块承载微前端模式判断

Decision:
主应用与两个子应用继续复用现有平台级 localStorage 会话 key 与 `/auth/login`、`/auth/profile`、`/auth/logout` 接口。每个子应用新增集中式微前端运行时模块，用于判断是否运行在 `qiankun` 中、提供路由 base、容器节点与初始用户信息；页面、composable 和业务 API 不直接感知 `qiankun`。

Rationale:

- 当前 OA 与 SCRM 已经共享平台级 token key，本次无需再引入额外的宿主登录协议或自定义桥接层。
- 将微前端环境判断收敛到 runtime 模块中，可以避免在页面或 store 中到处写 `window.__POWERED_BY_QIANKUN__` 这类硬编码判断。
- 保持领域业务逻辑与运行容器解耦，后续无论替换微前端方案还是恢复独立运行，改动范围都会更小。

Alternatives considered:

- 宿主向子应用强制下发所有用户态并阻止子应用自行取 profile：能减少一次请求，但会让子应用过度依赖宿主。
- 为主应用单独设计一套会话同步协议：复杂度过高，本次没有必要。

### 5. 路由采用“宿主前缀 + 子应用内部路径”模型

Decision:
主应用把 OA 页面统一挂在 `/oa/**`，SCRM 页面统一挂在 `/scrm/**`。子应用 router 在独立运行时使用 `/` 作为 base，在 `qiankun` 宿主模式下分别使用 `/oa` 与 `/scrm` 作为 base，并继续复用原有内部子路径。

Rationale:

- 路由前缀稳定后，宿主菜单跳转、首次可访问页面兜底和浏览器刷新都更容易保持一致。
- 子应用内部路径几乎不需要改名，只要切换 base 即可延续现有页面层级和守卫逻辑。
- 未来新增更多子应用时，只需为其分配新的顶级前缀和菜单分组，不必重写整套路由模型。

Alternatives considered:

- 宿主与子应用共用同一扁平路径空间：会让不同域的页面命名冲突风险变高，也不利于区分当前激活子应用。
- 让宿主通过 hash 驱动子应用：实现可以简化，但不符合当前项目已经统一采用 history 路由的约定。

### 6. 主应用视觉系统使用 `ui-ux-pro-max` 推荐方案的“收敛版 Enterprise Gateway”

Decision:
主应用采用 `ui-ux-pro-max` 输出的 `Enterprise Gateway` 信息架构方向，并吸收 `Liquid Glass` 的材质语言，但在后台场景中收敛透明度、动效速度和光晕强度。视觉上使用冷静青蓝与深海军蓝作为主轴，辅以绿色 CTA 和暖色提醒，通过统一 CSS 变量管理背景、表面、边框、标题、标签与交互状态。

Rationale:

- 该方向适合“统一门户 + 多业务域入口”的产品语义，能够同时表达平台级入口感和后台可读性。
- 对 `Liquid Glass` 做收敛后，既能保留高级感和品牌识别，也不会牺牲高信息密度后台的可扫读性。
- 统一语义变量后，宿主登录页、导航壳层和加载态都可以复用同一套设计令牌，维护成本更低。

Alternatives considered:

- 完全延续 `scrm-web` 现有样式：最省事，但无法体现“主应用门户”的新身份。
- 继续沿用 `oa-web` 的安静办公风格：适合流程页面，但不够表达集团级统一入口与跨域导航。

## Risks / Trade-offs

- [Risk] `qiankun` + Vite 子应用接入会增加入口层复杂度 -> Mitigation: 将生命周期、base 计算、容器挂载点和宿主模式判断集中到独立 runtime 模块，避免扩散到页面层。
- [Risk] 主应用维护自己的菜单注册表，可能与子应用实际路由产生漂移 -> Mitigation: 菜单配置只维护稳定的页面入口和文案，不推断子应用内部细节；新增页面时同步更新 OpenSpec 与宿主菜单配置。
- [Risk] 子应用在宿主模式下隐藏壳层后，部分页面可能丢失原本由子应用 topbar 提供的上下文 -> Mitigation: 由主应用统一补齐页面标题、副标题与分组标签，确保页面切换后仍有稳定定位。
- [Risk] 开发联调需要同时启动主应用和两个子应用，复杂度高于单应用 -> Mitigation: 在根脚本中提供显式联调入口，并保留独立启动子应用的路径，降低不同场景下的启动成本。
- [Risk] 主应用与子应用共享会话存储，如果宿主和子应用对登录态处理不一致，可能出现状态闪烁 -> Mitigation: 统一沿用现有平台级 key，并让主应用与子应用在启动时都通过同一套 profile 链路兜底。

## Migration Plan

- 第一步：新增 `main-web` 工作区，并接入主应用依赖、统一 auth store、router、菜单注册表和视觉样式令牌。
- 第二步：在 `main-web` 中注册 `oa-web` 与 `scrm-web` 两个 `qiankun` 子应用，补齐子应用容器、加载态与错误兜底。
- 第三步：分别改造 `oa-web` 与 `scrm-web` 的入口、router 和布局，使其支持宿主模式与独立运行双模式。
- 第四步：更新根级脚本、README 与开发说明，使主应用联调流程可操作、可验证。
- 第五步：运行主应用、子应用与根级校验，确认登录、菜单跳转、子应用加载和独立启动都正常。
- 回滚策略：若联调过程中出现不可接受问题，可移除 `main-web` 与 `qiankun` 相关接入，子应用因继续保留独立入口而可快速恢复到当前双应用并行模式。

## Open Questions

- 当前主应用先统一承载 OA 与 SCRM 的一级导航和标题区；后续是否需要进一步把子应用内部面包屑也收敛到宿主侧，可以等真实使用反馈后再提出独立 change。
