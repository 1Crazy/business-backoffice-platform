## Context

当前多后台体系已经形成了两层视觉结构：`oa-web` 与 `scrm-web` 共享一套基础后台组件语言，并通过各自主题覆盖表达业务气质；`main-web` 作为统一宿主，则在登录页、宿主壳层和平台治理原生页面上单独维护了一套更偏玻璃感的实现。随着平台治理页引入 `el-tabs`、表格、分页、对话框等结构，主系统与子系统之间开始出现明显分叉，尤其体现在 tab 结构、交互反馈、标题字体和壳层配色上。

这次变更是跨多个样式入口的收敛工作，既涉及 `main-web` 全局 token，也涉及宿主桌面/移动导航和平台治理页，同时需要处理宿主与 `oa-web`、`scrm-web` 在 `qiankun` 承载下共享 `Element Plus` 裸类名带来的样式串扰风险。

## Goals / Non-Goals

**Goals:**
- 让 `main-web` 原生页面复用与 `oa-web`、`scrm-web` 同一套后台组件节奏，尤其是 tab、表格、按钮、输入框、分页与空态。
- 为主系统壳层定义更克制稳定的宿主主题覆盖，让侧边栏、顶部标题区与移动菜单表达“统一门户”而不是某个业务子域。
- 收敛 host 与 subapp 的全局组件样式边界，避免在切换 OA、SCRM 与平台原生页时发生样式残留或覆盖。
- 建立可以重复执行的验证路径，确认主系统平台治理页与代表性子系统页面之间不再出现明显视觉割裂或样式串扰。

**Non-Goals:**
- 不重做 `oa-web` 或 `scrm-web` 的现有主题。
- 不在本次变更中抽取新的跨应用样式包或设计系统依赖。
- 不改变现有导航结构、权限逻辑或微前端挂载机制。

## Decisions

### Decision: 先让 `main-web` 补齐共享结构化组件皮肤，再保留宿主级主题覆盖

`oa-web` 与 `scrm-web` 已经在全局样式中对 `Element Plus` 的基础结构做了统一收口，`main-web` 当前缺失这一层，导致平台治理页 tab 和表格天然长得不像子系统。本次优先在 `apps/main-web/src/styles/global.css` 中补齐全局组件样式，让主系统先回到同一套结构语言上，再通过宿主壳层局部变量保留主系统的中性门户气质。

选择这种方式，而不是继续在 `PlatformGovernancePage.vue` 做局部补丁，是为了避免后续新增原生平台页面时继续复制零散样式。

### Decision: 主系统壳层采用更轻的 slate + sage 宿主主题

主系统不应看起来像 OA 的办公子域，也不应像 SCRM 的深色经营子域。宿主壳层会继续保留“统一门户”的中性身份，但将从上一轮偏重的深海军蓝压低饱和度，改成更轻的 slate + sage 组合：侧边导航维持清晰的宿主识别，同时减弱厚重感；顶部标题区、标签和按钮则转向更克制的石板灰与鼠尾草色点缀。

相比继续沿用偏亮的青色玻璃感，或者继续维持上一轮偏深的宿主色板，这种方案更容易同时承托平台治理原生页与嵌入态 OA/SCRM 内容，不会让宿主壳层与业务内容争夺视觉主导权。

### Decision: 优先通过样式作用域修复串扰，而不是重新开启 qiankun 实验性样式隔离

当前仓库安装的是 `qiankun@2.10.16`，接口仍然暴露 `sandbox.experimentalStyleIsolation` 与 `sandbox.strictStyleIsolation`。但宿主运行时代码已经记录过：实验性样式隔离在当前 Vite 子应用组合下会触发白屏。与此同时，`oa-web`、`scrm-web` 和 `main-web` 都在直接覆盖全局 `.el-button`、`.el-tabs__item`、`.el-table` 等裸类名，这才是串扰根源。

因此本次优先采用“显式作用域边界”策略：
- `oa-web` 与 `scrm-web` 的全局组件皮肤收敛到各自根类名之下，避免卸载后残留规则继续影响宿主或另一个子应用。
- `main-web` 的共享组件皮肤只在主系统原生页面语境下启用，避免宿主样式覆盖嵌入态子应用内容。

这样可以在不重新启用风险较高的实验性隔离配置前提下，先把样式边界拉清楚。

### Decision: 验证以“主系统原生页 + 代表性子系统页”对照为主

这次问题不是单页 bug，而是宿主与子系统之间的整体观感分叉。因此验证不能只看主系统单页是否好看，而要直接对照：
- 主系统平台治理页的 tab 与结构化组件
- SCRM 代表性 tab 页面
- OA 代表性壳层页面

为了避免依赖完整后端链路，本次浏览器验证优先采用本地前端服务加 mock 数据的方式，重点确认壳层、页签、表格和状态反馈的一致性。

## Risks / Trade-offs

- [主系统主题继续摇摆，收敛不到用户满意的稳定气质] → 使用更低饱和度的 slate + sage 组合，并通过浏览器截图直接对照宿主与子系统并置观感。
- [全局 `Element Plus` 样式边界调整影响子应用独立模式或弹层样式] → 保留独立模式对应的 `body[data-*-standalone]` 入口，并在宿主模式下使用根容器作用域收口；重点回归独立页、嵌入页和 append-to-body 弹层相关页面。
- [浏览器验证依赖后端导致执行成本过高] → 使用本地 mock 数据验证视觉一致性与串扰修复，把这次检查聚焦在壳层、页签、按钮和表面层级，而不是业务接口联调。
