## Context

当前仓库已经形成 `apps/oa-web` 与 `apps/scrm-web` 两个 Vue 3 + Element Plus 前端应用，但视觉层仍以页面内零散写死样式为主：全局变量较少，布局壳层、登录页、导航、卡片与指标区各自为政，导致两个系统既没有形成稳定的共享语言，也没有真正拉开产品气质。源码巡检显示，两个应用都主要通过 `src/styles/global.css`、`src/layout/*` 与首页级页面组件承载视觉骨架，因此这次改造适合从“设计令牌 + 壳层 + 首屏”三层推进，而不是直接逐页重画。

技术约束如下：

- 现有前端栈为 Vue 3、Vite、Pinia、Element Plus，改造应优先复用现有组件库而不是引入新的重型 UI 框架。
- 仓库已存在多个后台应用，设计系统必须支持“共享基线 + 应用覆盖”，避免把 OA 与 SCRM 又做成两套完全割裂的实现。
- 后端接口契约不需要因为样式升级而变更，首阶段重点是结构与表现层重构。
- 需要保留轻量实现路径，使后续客户、线索、审批、公告等页面能增量迁移，而不是要求一次性整体重写。

## Goals / Non-Goals

**Goals:**

- 建立跨 `oa-web` / `scrm-web` 的共享后台视觉语言，包括颜色语义、阴影、圆角、边框、间距、状态与动效规则。
- 为 OA 定义“企业工作门户”主题，为 SCRM 定义“数据控制台”主题，在共享壳层基础上做主题级分化。
- 重构登录页、应用壳层与首页首屏，使用户在 5 秒内感知当前系统定位与核心操作路径。
- 让后续业务页面可以通过复用主题令牌与页面容器样式继续升级，而不是继续堆写局部 CSS。
- 在实现层明确响应式、键盘可达性与 reduced-motion 基线，避免“好看但脆弱”的前端样式升级。

**Non-Goals:**

- 不在本次规划中引入新的前端 UI 框架、图表库或设计平台。
- 不在本次规划中修改后端接口、权限模型或统计口径。
- 不追求一次性把两个应用所有业务页面全部翻新；首阶段以登录页、壳层和首页级关键页面为主。
- 不将 OA 与 SCRM 强行统一成单一视觉皮肤，两者仍然需要保留不同的产品语气与信息密度。

## Decisions

### Decision: 采用“共享语义令牌 + 应用主题覆盖”的两层设计系统

两个应用都保留 CSS 变量驱动，但变量将从当前零散的颜色常量升级为语义令牌，例如 `--surface-default`、`--surface-elevated`、`--text-primary`、`--accent-primary`、`--border-subtle`、`--shadow-card`、`--radius-lg`、`--space-6`。共享语义层保证布局、卡片、表单、状态和空态行为一致；应用主题层只覆盖品牌色、强调色、背景氛围和部分装饰强度。

这样做的原因：

- 可以让 `oa-web` 与 `scrm-web` 共享实现策略，但不共享最终气质。
- 后续业务页面迁移时只需接入语义令牌，不必重新决定每个页面的色值与阴影。
- 比直接重写 Element Plus 主题更轻量，且更适配当前仓库已有 scoped style 写法。

备选方案：

- 方案 A：两个应用分别做独立主题，不建立共享语义层。优点是自由度高；缺点是维护成本高，后续会继续分叉。
- 方案 B：强行共用一套后台皮肤。优点是开发快；缺点是无法体现 OA 与 SCRM 的产品差异。

### Decision: 先升级三类高杠杆入口，而不是平均分散到所有页面

首阶段以三类入口作为改造支点：

- 登录页：负责建立第一印象与系统身份。
- 应用壳层：负责导航、用户上下文、页面标题、面包屑与内容容器的一致性。
- 首页关键页面：OA 工作台与 SCRM 看板负责把设计语言转化为真实业务节奏。

这样做的原因：

- 这三类入口覆盖了用户最频繁接触的视觉面貌。
- 它们决定后续客户、线索、审批、公告等页面该如何复用页面壳层与内容组件。
- 能在控制范围内尽快证明视觉升级的价值，而不需要一次性改完所有业务模块。

备选方案：

- 方案 A：先从全局变量开始，不动具体页面。风险是用户很难感知变化。
- 方案 B：从所有业务页同时铺开。风险是范围失控，且容易出现局部风格不一致。

### Decision: OA 与 SCRM 首页采用不同的信息结构策略

OA 首页采用“任务聚合 + 快捷动作 + 信息提醒”结构，首屏重点是待办优先级、快捷入口和公告摘要，整体气质更安静、更可信，减少过度数据化表达。SCRM 首页采用“筛选条 + KPI 卡 + 洞察模块”结构，强调筛选效率、数字对比与运营扫描节奏，允许更高信息密度与更明确的强调色。

这样做的原因：

- OA 用户的目标是快速进入办公流转，而不是长时间停留在数据面板里。
- SCRM 用户更需要基于指标做判断，因此数据密度与过滤交互优先级更高。
- 同样是后台应用，但角色心智不同，不能继续共用近似的首页模版。

备选方案：

- 方案 A：两个应用都采用统一 KPI + 卡片首页。优点是实现简单；缺点是丢失产品语义。

### Decision: 使用“增强 Element Plus 容器表现 + 自定义壳层样式”而非深度替换组件体系

改造将优先通过页面壳层、自定义卡片容器、CSS 变量覆盖和局部组件样式增强来实现，而不是重写完整组件库。表单、表格、弹窗等仍继续基于 Element Plus，只调整它们在当前主题中的边框、阴影、标题、空态和交互反馈。

这样做的原因：

- 与现有代码结构兼容度最高，风险最小。
- 能把精力集中在真正影响观感的壳层、节奏、间距与信息结构上。
- 不会引入额外组件抽象债务，适合增量重构。

备选方案：

- 方案 A：引入新的设计系统或组件库。优点是上限高；缺点是迁移与学习成本显著增加。

### Decision: 浏览器验收纳入样式升级定义完成标准

这次变更不仅依赖静态代码 review，还需要通过浏览器检查登录页与首页级页面在桌面宽度和窄屏宽度下的视觉结果。验收关注点包括：首屏层级、导航稳定性、色彩对比、按钮聚焦态、空态与 reduced-motion 兼容。

这样做的原因：

- 样式升级很容易在代码层看起来合理，但真实浏览器里出现密度失衡、换行、对比不足或阴影过重。
- 用户明确要求通过浏览器打开页面看样式，这应成为本次变更的一部分。

## Risks / Trade-offs

- [共享令牌设计过粗，无法覆盖两个应用差异] → 通过“共享语义层 + 应用覆盖层”拆分，并在首页先验证差异是否足够明显。
- [过度追求视觉表现导致后台使用效率下降] → 优先优化信息节奏、可扫描性与关键动作，不引入重装饰和过量动效。
- [Element Plus 默认样式与自定义壳层冲突] → 将改动集中在容器、变量和有限组件覆写，避免全量深度覆盖内部结构。
- [只改首页导致二级页面风格断层] → 在设计系统中先定义通用卡片、表格、表单、抽屉和状态样式基线，确保后续页面有迁移模板。
- [浏览器验证依赖本地服务环境] → 优先通过 mock 数据验证页面结构与样式，再在具备后端环境时补做真实接口联调验证。

## Migration Plan

1. 先建立共享语义令牌与两个应用的主题变量，统一全局背景、文字、边框、阴影与基础动效。
2. 重构登录页、侧边栏、顶部栏和内容容器，让应用壳层稳定下来。
3. 升级 OA 工作台与 SCRM 看板首屏模块，验证两种产品气质是否拉开。
4. 将卡片、表格、筛选栏、空态与状态标签规范扩散到二级业务页面。
5. 通过浏览器截图和响应式检查完成视觉回归验收。
