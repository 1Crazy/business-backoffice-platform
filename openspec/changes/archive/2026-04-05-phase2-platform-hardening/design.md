## Context

当前仓库已经完成一期 SCRM MVP，并在单仓库内交付了前端后台、NestJS API、Prisma schema 和本地 Docker 工作流。现状可以支撑“登录 -> 客户/线索 -> 跟进 -> 看板 -> 系统管理”的主流程，但仍然带有明显的 MVP 特征：

- 客户、线索和审计日志接口默认返回全量列表，缺少统一的分页和排序契约。
- 数据权限逻辑散落在多个 service 中，目前主要依赖 `super-admin`、`sales-manager` 和员工本人三个硬编码分支，且“团队范围”仅覆盖直接部门，不覆盖子部门。
- 认证仍然是纯登录式 JWT，缺少刷新、主动退出、会话撤销和账号停用后的即时失效机制。
- 附件直接写入本地磁盘，并把物理路径暴露为业务元数据的一部分，不利于后续迁移到对象存储或实现下载鉴权。
- 仓库缺少 CI 入口，二期变更虽然有 OpenSpec，但没有把 lint/test/build 作为仓库级交付门槛。

二期后续规划会继续进入企业微信、自动化营销和更复杂的运营分析。如果不先完成这一轮平台硬化，后续 change 会不断在“列表性能、权限口径、会话治理和存储抽象”上返工。

## Goals / Non-Goals

**Goals:**

- 为客户、线索、提醒和审计日志建立统一的分页查询和排序契约。
- 建立一套可复用的数据范围解析机制，让业务列表、详情、提醒和看板共用同一份访问边界。
- 将后台认证升级为可撤销、可续期的会话模型，覆盖刷新、退出和账号停用失效。
- 将附件读写升级为存储抽象，保留本地实现，同时为后续对象存储接入保留稳定接口。
- 把 lint、test、build 固化为仓库级自动校验，确保 phase-two 迭代具备持续交付基线。

**Non-Goals:**

- 不在本次 change 中接入企业微信、短信、邮件或自动化营销规则。
- 不在本次 change 中引入多租户隔离、计费或插件化扩展。
- 不在本次 change 中拆分微服务，也不把 Redis、消息队列或对象存储作为必需前置条件。
- 不在本次 change 中实现异步导出中心、复杂报表引擎或新的业务域模型（如商机、合同）。

## Decisions

### 1. 统一业务列表为偏移分页契约

Decision:
客户、线索、提醒和审计日志列表统一采用偏移分页，接口返回 `items`、`page`、`pageSize`、`total` 和排序信息；前端列表页同步改为服务端分页。

Rationale:

- 当前后台是典型管理端表格场景，用户需要跳页、按列排序和保留筛选条件，偏移分页更贴合这一类交互。
- 当前仓库前后端都在同一个 monorepo 中，可以接受一次协调更新，不必为了向后兼容保留双份接口。
- 统一契约后，后续要补批量操作、导出或缓存时不需要再逐页改造每个模块。

Alternatives considered:

- Cursor pagination：更适合高并发滚动场景，但对传统后台“跳到第 N 页”的支持较差。
- 继续返回全量数组，由前端本地分页：实现简单，但数据量放大后会同时带来性能和权限收口问题。

### 2. 数据范围继续附着在角色模型上，并通过共享解析器统一计算

Decision:
在现有 RBAC 基础上为角色增加 `dataScope` 枚举，至少覆盖 `SELF`、`DEPARTMENT`、`DEPARTMENT_AND_SUBTREE` 和 `ALL`。服务端新增共享的数据范围解析器，统一计算当前用户可见的部门和归属人集合；用户拥有多个角色时，数据范围取这些角色中的最大可见范围。

Rationale:

- 当前权限模型已经以角色为中心，继续把数据范围附着在角色上，改造成本最低，也最符合后台运营角色的配置习惯。
- 统一解析器可以消除 `customers`、`leads`、`dashboard` 中重复的 owner 过滤逻辑，避免不同模块出现不同口径。
- “取最大可见范围”与当前权限并集模型一致，便于理解和测试。

Alternatives considered:

- 为每个用户单独配置数据范围：灵活，但会显著增加管理复杂度和 UI 负担。
- 引入 ABAC 或策略引擎：扩展性更强，但超出当前单租户后台的必要复杂度。

### 3. 子部门范围通过 PostgreSQL 递归查询解析，而不是新增闭包表

Decision:
部门层级仍然保持现有邻接表模型，通过 PostgreSQL 递归查询解析子部门集合，并由共享数据范围解析器复用该能力。

Rationale:

- 当前已经有 `Department.parentId`，继续沿用现有模型可以减少 schema 和维护成本。
- PostgreSQL 原生支持递归查询，足以支撑当前单租户后台的组织树规模。
- 在真正出现超大组织树之前，没有必要为了一个还未出现的性能瓶颈引入闭包表或额外同步逻辑。

Alternatives considered:

- 新增部门闭包表：查询更快，但写入和维护逻辑更复杂。
- 在应用层递归多次查询：实现简单，但会带来明显的 N+1 风险和重复代码。

### 4. 会话治理采用“短时访问令牌 + 持久刷新会话”模型

Decision:
新增 `UserSession` 持久化模型，保存刷新令牌的哈希值、过期时间、撤销状态和基础会话元数据。访问令牌改为短有效期，并携带 `sessionId`；受保护请求在鉴权时同时校验用户状态和会话状态。

Rationale:

- 纯 JWT 无法可靠支持主动退出、会话撤销和账号停用后的即时失效。
- 使用持久化会话可以在不引入 Redis 的前提下满足二期需要的治理能力。
- 将刷新令牌只存哈希值，能降低数据库泄漏后的直接风险。

Alternatives considered:

- 继续使用纯 JWT：最轻量，但无法满足硬化目标。
- 只增加 `tokenVersion`：能处理批量失效，但对单会话退出和刷新令牌管理不够友好。
- 切换到服务端 Cookie Session：也可行，但需要同步调整当前前后端分离和 Swagger 的使用方式。

### 5. 附件能力升级为存储驱动接口，默认继续使用本地磁盘

Decision:
抽象统一的附件存储驱动接口，默认提供本地磁盘实现，并将数据库中的附件字段从“原始磁盘路径”转向“存储提供方 + 存储键 + 展示元数据”。附件下载统一通过受权限保护的 API 入口完成。

Rationale:

- 这能保留当前本地 Docker 工作流，又不会把未来对象存储接入变成破坏性重构。
- 通过 API 下载能把业务访问控制落到服务端，而不是依赖静态文件目录暴露。
- 元数据与存储实现解耦后，迁移到 S3/OSS/MinIO 时无需改动业务模块的关联关系。

Alternatives considered:

- 继续把磁盘路径直接暴露到业务层：实现最简单，但后续迁移和鉴权都比较脆弱。
- 现在就强制上对象存储：对本地开发和二期起步来说，依赖过重。

### 6. 仓库交付采用单体原子升级，不引入 API 版本分叉

Decision:
本次 change 直接升级现有前后端接口契约，不为分页返回结构和会话接口另开 `v2` 路径；通过单仓库同版本发布保持前后端一致。

Rationale:

- 当前 web 和 api 共同维护，且只有内部管理端使用，没有外部第三方依赖这些接口。
- 保持单份接口可以避免同一业务流程长期维护两套返回结构。
- Docker 和 monorepo 已经天然支持原子升级。

Alternatives considered:

- 保留旧接口并新增版本化路径：向后兼容更强，但对当前场景会增加长期维护负担。

## Risks / Trade-offs

- [Risk] 鉴权时增加会话校验会提高数据库访问频率 -> Mitigation: 访问令牌只校验最小必要字段，按 `sessionId` 和 `userId` 建索引，并保持访问令牌较短 TTL。
- [Risk] 数据范围从硬编码逻辑迁移到角色配置后，默认角色如果映射错误会引发可见性变化 -> Mitigation: 迁移脚本为现有系统角色写入与当前行为一致的默认值，并补充回归测试。
- [Risk] 分页返回结构会破坏当前前端页面和测试 -> Mitigation: 在同一个 change 中同步更新 web、api 和测试，避免半升级状态。
- [Risk] 下载统一走 API 会增加后端带宽压力 -> Mitigation: 存储驱动保持可扩展，后续如有大文件场景可切换为签名 URL。
- [Risk] 子部门递归查询在组织树扩大后可能变慢 -> Mitigation: 将递归逻辑集中在一个解析器中，后续需要升级为闭包表时只改这一层。

## Migration Plan

- 第一步新增数据库迁移，补充角色数据范围字段、用户会话表和新的附件存储元数据字段。
- 第二步更新种子数据，为当前系统角色写入默认数据范围，使现有账号上线后仍保持接近一期的可见行为。
- 第三步实现共享数据范围解析器、统一分页 DTO/响应结构和新会话能力，再改造客户、线索、提醒、看板和审计模块。
- 第四步同步更新前端页面、状态管理和测试，使所有列表与认证流程都切换到新接口契约。
- 第五步增加 CI 工作流，把 lint、test 和 build 设为仓库级交付门槛。
- 部署策略采用前后端原子发布；回滚时优先回退代码与路由流量，新增的 schema 字段和会话表保持向后兼容，不要求先做数据回滚。

## Open Questions

- 本次 change 是否只提供“当前会话退出”，还是要同时支持管理员查看并撤销指定员工的全部活动会话。
- 附件下载是否需要在本次就加入一次性下载链接，还是先以受保护 API 直出为主。
- 审计日志是否需要在本次就支持导出，还是先完成分页筛选并将导出留到后续 change。
