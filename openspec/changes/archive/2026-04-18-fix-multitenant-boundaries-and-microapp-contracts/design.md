## Context

当前代码库已经完成 Prisma 多租户字段扩展，但 OA、workflow、开放平台更新链路和微前端宿主契约没有同步完成彻底收口。结果是部分模块只在 service 层“约定式”携带租户上下文，repository 仍允许全局查询或按主键更新；宿主壳层和子应用又分别维护了一套页面权限与登录失效跳转规则，导致运行时行为分叉。

这次修复横跨 `apps/api`、`apps/main-web`、`apps/oa-web`、`apps/scrm-web`，属于跨模块安全与契约收敛变更，必须先把边界决策写清楚再落代码。

## Goals / Non-Goals

**Goals:**
- 让 OA、workflow 和开放平台更新链路在 repository 层显式使用 `tenantId`，不再依赖调用方记忆。
- 让 OA 的创建、审批、检索、公告和通讯录接口全部只返回当前租户数据。
- 让 workflow 模板、实例、任务、审批人解析和抄送链路具备租户约束，并为后续模块继续复用相同模式。
- 让宿主菜单权限、子应用页面权限和登录失效跳转行为保持一致。
- 让租户级系统管理页面不再直接读取或操作平台级治理配置。

**Non-Goals:**
- 不重做现有权限模型或重新设计角色体系。
- 不引入新的微前端通信协议或 qiankun 全局状态总线。
- 不新增平台治理 UI，只收紧已有入口的可见性与后端边界。
- 不在这次 change 中把所有历史模块统一重构成新的 base repository 抽象。

## Decisions

### 1. 租户约束下沉到 repository 契约，而不是继续放在 service 约定里

OA、workflow 和开放平台的核心读写会改成“入参必须包含 `tenantId` 或 actor 派生 tenantId，repository 内部必须使用它构造 `where` 或 `data`”。这样可以把跨租户风险拦在最靠近数据层的位置。

备选方案：
- 仅在 service 层补更多断言。放弃，因为调用链一长就容易再次漏掉。
- 用 Prisma middleware 全局注入租户过滤。当前仓库查询模式复杂，短期改动风险更高，不适合作为这次止血方案。

### 2. OA 模块按“当前租户业务空间”而不是“当前用户 ID 相关记录”建模

OA 的工作台、公告、通讯录、审批和申请列表都必须同时满足“用户相关”和“租户相关”两个条件。创建申请时显式写入 `tenantId`，读取与统计时显式带 `tenantId`，默认审批人也只在当前租户内解析。

备选方案：
- 继续按 `applicantId` / `approverId` 过滤，假设用户不会跨租户复用。放弃，因为模型已经允许平台级用户和租户级用户并存，这个假设不稳。

### 3. workflow 以租户级模板和租户级运行时为默认模式

workflow 的模板、节点、实例、任务、动作和抄送记录都已经有 `tenantId` 字段，因此 service 和 repository 统一改成租户级读写。平台级模板如果未来需要保留，将通过显式平台语义单独扩展，而不是继续复用“tenantId 为空”的隐式模式。

备选方案：
- 允许 workflow 同时继续读 `tenantId = null` 的模板。放弃，因为当前需求重点是修复跨租户问题，不宜保留模糊行为。

### 4. 宿主导航权限是唯一页面权限来源，子应用路由必须与之对齐

对于 `main-web` 承载的 `/oa/**`、`/scrm/**` 页面，宿主导航项权限和子应用内部对应路由权限必须使用同一权限键。任何“宿主菜单 A、子应用页面 B”的组合都视为契约错误。

备选方案：
- 保持双份定义，通过注释约定同步。放弃，因为已经证明这会漂移。

### 5. 微前端模式下的登录失效跳转统一回到宿主登录页

当 `oa-web` 或 `scrm-web` 运行在 qiankun 宿主模式下，鉴权失败或用户主动从无权限页跳回登录时，必须跳转宿主的 `/login`，不能继续使用子应用 base 下的 `/oa/login`、`/scrm/login`。

备选方案：
- 在宿主补 `/oa/login`、`/scrm/login` 兼容路由。放弃，因为这会固化错误边界，并让认证入口继续分裂。

### 6. 平台级治理接口与租户级系统管理页面分离

`system-governance` 里的通知通道、存储配置和调度任务属于平台级能力，不再通过 `dictionary:read/write` 暴露给租户级系统管理页面。当前修复以“收紧权限和前端入口”为主，后续如需平台运营台入口，再单独通过平台权限暴露。

备选方案：
- 继续复用 `dictionary:*` 作为治理权限。放弃，因为它会把业务字典治理与平台基础设施治理混成一层。

## Risks / Trade-offs

- [Risk] 收紧 repository 契约后，部分旧测试或调用点会因为缺少 `tenantId` 直接失败。 → Mitigation: 先修服务入口与测试夹具，再运行模块测试回归。
- [Risk] workflow 如果强制只读当前租户模板，历史 `tenantId` 为空的数据会暂时不可见。 → Mitigation: 本地种子和迁移已提供默认租户回填，这次实现以当前已迁移数据为准。
- [Risk] 隐藏系统治理入口后，现有 SCRM 系统管理页展示内容会减少。 → Mitigation: 保留租户级开放平台、审计、批处理等入口，只移除平台级治理块。
- [Risk] 宿主和子应用权限键统一后，部分角色配置会暴露之前的错误授权。 → Mitigation: 选择以宿主导航契约为准，对齐子应用路由定义，并保留无权限兜底页。
