## Context

多前端工作区能力已经落地，当前仓库的应用拓扑变成了：

```text
scrm-web  --->  apps/api  --->  PostgreSQL
oa-web    --->     ^
                   |
         Auth / Users / Roles / Departments / Dictionaries / Uploads
```

这意味着“新增 OA”现在真正要解决的问题，不再是工作区命名，而是以下三层边界：

- 平台层：账号、权限、部门、员工、附件、字典是否继续复用。
- OA 业务层：首批到底是做完整 OA 套件，还是先落一个可运行的最小办公协作闭环。
- 体验层：OA 前端是否沿用 SCRM 视觉，还是建立一个独立但兼容的设计语言。

当前代码库中有几个现实约束：

- `apps/api` 仍然是模块化单体，适合继续扩展业务模块，而不是马上拆成多个服务。
- `Permission` 当前只有 `group` 等字段，没有应用命名空间；seed 也只有 SCRM 权限。
- `scrm-web` 会话 key 仍使用 `scrm-token`、`scrm-refresh-token` 等应用专属命名，不利于未来多应用复用登录态。
- `scrm-web` 当前视觉偏“轻盈蓝色运营后台”，更适合销售与运营场景，不适合直接一比一复刻为 OA。

因此本次 change 的关键，不是“再做一个和 SCRM 一样的后台”，而是定义一套平台复用边界清楚、OA 业务范围克制、视觉语言能区分产品心智的落地方案。

## Goals / Non-Goals

**Goals:**

- 新增 `apps/oa-web`，作为独立的 OA 后台前端应用。
- 在复用统一账号体系的前提下，把权限模型扩展为支持 `scrm`、`oa` 等应用维度。
- 以模块化单体方式在 `apps/api` 内新增 OA 业务模块，而不是提前拆微服务。
- 明确 OA 第一阶段的真实业务边界，优先形成“能跑的办公协作闭环”。
- 基于 `ui-ux-pro-max` 为 OA 制定独立的浅色结构化设计系统，并将其约束到后续页面骨架中。

**Non-Goals:**

- 不在本次 change 中引入 `oa-api`、微服务网关、消息队列或分布式事务治理。
- 不在本次 change 中实现通用流程设计器、动态表单平台、BPMN 编排器或流程画布。
- 不在本次 change 中实现复杂考勤打卡、硬件设备接入、薪酬或财务报销全套能力。
- 不在本次 change 中抽离大而全的前端共享包；共享约定优先于共享实现。
- 不要求 OA 首期覆盖传统 OA 的所有模块，只要求形成首批可用闭环。

## Decisions

### 1. `oa-web` 作为独立前端应用接入，而不是继续扩展 `scrm-web`

Decision:
新增 `apps/oa-web`，维持与 `apps/scrm-web` 对等的前端应用边界。OA 使用独立路由、布局、页面目录和构建产物，不作为 `scrm-web` 下的菜单分支存在。

Rationale:

- OA 与 SCRM 属于两个产品心智，部署节奏、信息架构和视觉语言都会逐渐分化。
- `support-multi-frontend-apps` 已经把第二个前端应用的工作区基础铺好了，现在应该真正使用这条路径。
- 独立应用边界更利于后续按产品线扩展，而不是把单应用后台无限做大。

Alternatives considered:

- 继续往 `scrm-web` 里加 OA 菜单：短期最快，但会重新把产品边界、权限边界和视觉边界耦回一个前端。
- 使用微前端加载 OA 子应用：当前没有必要，会引入过高的运行时复杂度。

### 2. 后端继续保持模块化单体，不做微服务拆分

Decision:
OA 继续接入现有 `apps/api`。后端以内聚模块的方式新增 OA 能力，例如请假、审批、公告与工作台聚合等，不在本次 change 中拆 `oa-api` 或微服务。

Rationale:

- 当前账号、角色、权限、部门、员工、附件与字典都具备显著的平台复用价值。
- 0 到 1 阶段最大的挑战在于边界澄清和业务闭环，而不是服务拆分。
- 提前拆分会把登录、权限、跨服务调用、日志追踪和部署复杂度一并拉高，但对首期价值帮助不大。

Alternatives considered:

- 直接拆 `oa-api`：只有当 OA 从 day 1 就是独立团队、独立发布和独立数据库边界时才更划算；当前不满足。
- 直接微服务化：对当前规模明显过度设计。

### 3. 权限目录增加应用命名空间，角色授权按应用维度分组

Decision:
将权限目录从“只有业务 group，没有应用归属”扩展为“同时带应用命名空间与业务分组”的模型。建议在权限实体中新增类似 `appCode` 的字段，并将现有 SCRM 权限回填为 `scrm`，新增 OA 权限标记为 `oa`。角色编辑与权限目录展示按应用维度分组。

Rationale:

- 没有应用命名空间，多前端场景下的权限目录会越来越混乱，角色编辑页面也无法清晰区分 SCRM 与 OA。
- 当前 `Permission.group` 更像模块分组，不足以表达“权限属于哪个产品应用”。
- 这一步完成后，同一个员工账号就能自然承载“有 SCRM 权限、没 OA 权限”或“两边都有权限”的场景。

Alternatives considered:

- 仅靠权限 code 前缀推断应用，例如 `oa:*`：可以作为兼容策略，但不利于后续目录展示和后台管理建模。
- 为每个应用单独维护一套角色体系：会割裂统一账号模型，后续维护成本更高。

### 4. 登录态改为平台级共享命名，但实现先保持应用内自洽

Decision:
前端会话存储从 `scrm-token` 这类应用专属 key 迁移为平台级命名，例如 `platform-access-token`、`platform-refresh-token`、`platform-session-expires-at`。`scrm-web` 与 `oa-web` 共用同一登录身份和续期链路，但本次不强制抽离单独共享包，先保持每个应用内部实现自洽。

Rationale:

- 同一员工账号在 SCRM 与 OA 间切换时，重复登录的体验很差。
- 平台级 key 能让多应用共用统一身份模型，又不要求立刻把所有实现收敛到一个共享包。
- 先统一契约、后决定是否抽包，更符合仓库当前“先共享约定，再共享实现”的原则。

Alternatives considered:

- 维持 `scrm-token` / `oa-token` 双 key：实现简单，但用户会拿到重复登录和双份会话状态。
- 立刻抽 `packages/platform-web`：长期可能成立，但当前还没有足够多前端应用验证抽象稳定性。

### 5. OA 首期只做“工作台 + 请假审批闭环 + 公告 + 通讯录”

Decision:
OA MVP 聚焦以下范围：

- 工作台：展示待办审批数、我发起的申请、公告摘要与快捷入口。
- 审批中心：至少包含“待我审批”“我发起的申请”两类视图。
- 请假申请：员工可发起请假，查看状态与审批轨迹。
- 公告通知：员工可查看公告列表、详情与发布时间。
- 组织通讯录：复用现有部门/员工基础数据，以 OA 视角提供只读查询。

Rationale:

- 这是最容易形成真实办公协作闭环的一组能力。
- 与当前已存在的组织、权限与用户数据复用度高。
- 能避免一开始就把 OA 范围拉进报销、出差、打卡、文档中心、知识库、流程引擎等重资产领域。

Alternatives considered:

- 先做完整 OA 套件：范围过大，无法在 0 到 1 阶段形成稳定闭环。
- 只做静态页面骨架：虽然快，但无法验证权限、流程和数据模型的真实边界。

### 6. 审批模型先做“固定业务流”，不做通用工作流引擎

Decision:
首期审批只围绕请假申请构建，使用固定业务流与审批动作轨迹，不设计通用流程模板、节点画布、表达式规则或动态表单引擎。实现上可以从“单当前审批人 + 操作历史”起步，后续如确有需求再演进。

Rationale:

- OA 最容易过度设计的地方就是“先做通用审批引擎”，但首期真正需要的是跑通一个可验证的审批闭环。
- 先做固定业务流可以更快暴露字段、状态机、通知和权限模型的真实需求。
- 留出未来升级空间，并不等于现在就要支付通用化成本。

Alternatives considered:

- 直接设计通用引擎：设计空间太大，容易让 change 被拖垮。
- 完全不建审批中心，只做表单提交：无法满足 OA 的核心价值。

### 7. OA 视觉系统采用浅色、结构化、强层级的信息工作台

Decision:
基于 `ui-ux-pro-max` 的检索结果，OA 前端采用“Minimalism & Swiss Style / Swiss Modernism 2.0”作为骨架风格，吸收 “Productivity Tool” 配色和 “Chinese Simplified” 字体建议，但显式放弃工具输出中的暗色企业门户和重玻璃态方向。视觉基线如下：

- 配色：
  - 主色使用偏效率与协作感的青绿色系，如 `#0D9488` / `#14B8A6`
  - 文字与主界面结构色使用深墨色与石板灰，如 `#0F172A` / `#334155`
  - 警示与待处理强调色使用暖橙，如 `#F97316`
  - 背景使用浅灰青或高亮中性色，如 `#F8FAFC` / `#F0FDFA`
- 字体：
  - 中文优先 `Noto Sans SC` / `PingFang SC` / `Microsoft YaHei`
  - 使用清晰的 12 / 14 / 16 / 20 / 28 级字阶，避免随机字号
- 组件与动效：
  - 使用 8px 间距体系
  - 卡片圆角控制在 12-16px，保留轻微阴影而非悬浮玻璃感
  - 动效控制在 150-250ms，强调状态切换，不做大幅缩放
- IA 与可访问性：
  - 深层页面提供面包屑
  - 审批与请假状态使用高对比标签体系
  - 标题层级严格递进，保证键盘可见焦点

Rationale:

- OA 是高频白天使用的生产工具，浅色结构化界面更适合长时间工作与表单/列表密集场景。
- 与现有 SCRM 的“运营看板式蓝色渐层”区分开来，有助于建立第二产品的认知边界。
- `ui-ux-pro-max` 给出的 dark mode / glass 方案更像企业官网或高概念 dashboard，不适合当前目标。

Alternatives considered:

- 直接沿用 `scrm-web` 的蓝色轻盈运营风格：复用成本低，但产品心智区分太弱。
- 按工具结果使用暗色玻璃态：不符合当前仓库的前端设计约束，也不适合 OA 高频使用场景。

## Risks / Trade-offs

- [Risk] 权限模型从单应用扩展到多应用，会波及 seed、角色目录、前端菜单和无权限兜底逻辑。
  Mitigation: 以 `appCode` 为最小增量建模，并优先更新角色目录 API 与前端分组展示。

- [Risk] 平台级会话 key 迁移会让现有 `scrm-web` 用户在升级后重新登录一次。
  Mitigation: 在 change 中把这件事视为可接受的一次性切换，并保持刷新逻辑不变。

- [Risk] 首期只做请假审批，可能被误解为 OA 范围过小。
  Mitigation: 在 proposal 和 design 中明确这是“首个闭环”而不是“最终边界”，为后续报销、出差等流程保留拓展口。

- [Risk] 如果 OA 页面完全复制 SCRM 结构，会失去独立产品识别度。
  Mitigation: 在 design 中明确 OA 的视觉语言、信息架构和页面原型方向，不允许简单换皮。

- [Risk] 不抽共享包可能在短期内带来少量重复代码。
  Mitigation: 先共享契约与命名，待 `oa-web` 稳定后再基于真实重复度决定是否抽取平台前端基础设施包。

## Migration Plan

- 第一步：更新 `access-control` 增量 spec，明确多后台应用共用账号、权限按应用维度建模。
- 第二步：新增 `office-automation-workspace` spec，定义 OA 首批业务闭环与基础体验要求。
- 第三步：实现权限 schema/seed/API 的多应用扩展，并把现有 SCRM 权限回填应用命名空间。
- 第四步：新增 `apps/oa-web`，完成 OA 前端壳层、设计 token、路由与首批页面骨架。
- 第五步：在 `apps/api` 内新增请假审批、公告与 OA 工作台所需聚合模块，完成首个业务闭环。
- 第六步：校验 `scrm-web`、`oa-web`、`apps/api` 的鉴权、构建、测试与权限场景都能在多应用模型下正确运行。

## Open Questions

- OA 首期的公告能力是否需要包含发布与撤回后台，还是先只做只读公告墙。
- 审批动作是否在首期就要支持抄送/转交，还是先聚焦审批通过与驳回。
- 后续是否需要补一个平台入口页或应用切换器，帮助拥有多个应用权限的员工在 `scrm-web` 与 `oa-web` 之间跳转。
