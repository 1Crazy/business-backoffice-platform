## Context

当前 OA 公告交互链路分成两段：

- `AnnouncementsPage.vue` 中的公告卡片通过 `RouterLink` 跳转到 `/announcements/:id`。
- `WorkspacePage.vue` 中的“最近公告”也复用同一条详情页路由。

这套实现虽然满足“能看到公告详情”，但会让用户离开当前浏览上下文。对于公告通知这类轻量、频繁扫读的信息，员工通常希望快速展开一条内容、读完后继续留在原列表或工作台，而不是被带到新的详情页面再返回。

另外，仓库中的 SCRM 已经存在多处详情抽屉交互，主应用也已经为子应用弹层补过宿主兼容规范。因此这次更适合把 OA 公告详情收敛为抽屉模式，并顺手处理旧详情路由的兼容跳转。

## Goals / Non-Goals

**Goals:**

- 让 OA 公告详情默认在当前页面上下文中通过抽屉打开，而不是进入独立详情页。
- 让公告列表页和工作台的公告入口复用同一套详情抽屉组件和加载逻辑。
- 保留旧 `/announcements/:id` 路径的访问兼容，避免已有链接直接失效。
- 在主应用承载 `oa-web` 时继续保证抽屉完整显示，不引入新的宿主裁切问题。

**Non-Goals:**

- 不调整公告后端接口契约，不新增编辑、发布或撤回能力。
- 不把 OA 中所有详情型页面统一改成抽屉；本次只覆盖公告通知详情。
- 不引入新的跨应用共享 UI 包或第三方状态管理依赖。

## Decisions

### 1. 公告详情收敛为可复用抽屉组件，而不是保留独立详情页作为主入口

Decision:
新增一个可在 OA 页面内复用的公告详情抽屉组件，并由页面侧状态编排控制打开、关闭和详情加载。公告列表和工作台摘要都使用这套组件，而不是继续跳到独立详情页。

Rationale:

- 公告阅读是“扫读后回到原上下文”的典型场景，抽屉比整页跳转更符合高频办公浏览节奏。
- 列表页和工作台都展示公告摘要，复用一套详情组件可以避免重复维护元信息、标题、摘要与正文排版。
- 抽屉可继续使用 `append-to-body`，与仓库中已有 SCRM 抽屉实现保持一致，也更适合主应用宿主场景。

Alternatives considered:

- 保留详情页，只把工作台里的入口改成弹窗：交互不一致，仍然保留两套详情承载方式。
- 改成 `el-dialog`：可行，但长文本阅读和元信息展示更适合侧边抽屉，且与现有详情抽屉模式更一致。

### 2. 使用路由 query 表达“当前打开的公告”，而不是继续维护专用详情子路由

Decision:
在 OA 页面中使用 `announcementId` 查询参数表达当前打开的公告详情抽屉；打开抽屉时写入 query，关闭时移除 query。旧 `/announcements/:id` 路径改为重定向到 `/announcements?announcementId=:id`。

Rationale:

- Query 方式可以让抽屉状态具备可刷新的地址表达，又不会制造新的深层详情页面。
- 同一套抽屉逻辑可以挂在公告列表页，也可以挂在工作台页，各页面都能在自身上下文内打开公告。
- 对旧链接做重定向比直接删路由更稳妥，能兼容收藏、历史记录或主应用已有隐藏路由入口。

Alternatives considered:

- 仅使用本地组件状态：实现最简单，但刷新后无法恢复当前打开的公告，也无法兼容旧详情链接。
- 继续保留详情页并在页面里弹出抽屉：路由语义和视觉交互相互冲突，复杂度更高。

### 3. 详情加载逻辑从“详情页专用 composable”改为“页面可复用的抽屉状态 composable”

Decision:
将当前基于 `route.params.id` 的公告详情加载逻辑改造成面向抽屉的共享 composable，负责同步 query、拉取详情、处理错误反馈和关闭逻辑。

Rationale:

- 现有 `useAnnouncementDetailPage` 与详情页路由强绑定，无法直接服务公告列表页和工作台两处入口。
- 抽屉状态包含“是否打开”“当前详情”“是否加载中”“打开/关闭动作”，更适合收口成复用 composable。

Alternatives considered:

- 在每个页面各自写一套详情请求与抽屉状态：容易重复，后续样式和行为难以保持一致。

## Risks / Trade-offs

- [Risk] 使用 query 表达抽屉状态会让地址栏在打开公告时发生变化。 → Mitigation: 仅使用单个轻量参数，并在关闭时清理，避免污染其他筛选参数。
- [Risk] 旧详情路由删除后若没有兼容跳转，历史链接会失效。 → Mitigation: 在 `oa-web` 与主应用路由侧都保留旧路径重定向。
- [Risk] 抽屉承载长文本时在移动端可能过窄。 → Mitigation: 参考仓库现有抽屉模式，在平板及以下宽度使用全屏抽屉。

## Migration Plan

- 第一步：补齐 proposal、design、tasks 与 `office-automation-workspace` 的 delta spec。
- 第二步：新增公告详情抽屉组件和共享 composable，完成公告列表页与工作台的接入。
- 第三步：把旧详情页路由改为重定向，并清理主应用中对应的隐藏详情入口定义。
- 第四步：补充 OA 页面测试并运行 `oa-web` 的类型检查与单测。
- 回滚策略：如抽屉模式出现不可接受问题，可恢复独立详情页路由与页面组件，同时移除 query 驱动逻辑。

## Open Questions

- 当前 query 名称计划使用 `announcementId`。如果后续 OA 其他页面也引入抽屉状态，需要再评估是否抽取统一的 query 命名约定，但这不阻塞本次实现。
