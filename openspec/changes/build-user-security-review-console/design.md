## 概览

本变更把已经存在的后端账号安全锁定状态，收敛成管理员可操作的前端治理工作台。总体思路是：

1. 不引入新后端状态机；
2. 复用现有 `GET /api/users` 和 `PATCH /api/users/:id/unlock`；
3. 在 `main-web` 平台治理原生页中增加“安全审核”视图；
4. 用筛选、摘要卡、详情抽屉和操作按钮组成最小但成熟的治理台。

## 设计决策

### 1. 工作台落在主应用平台治理原生页，而不是新建独立子应用

- 理由：
  - 账号安全审核本质上属于平台治理能力；
  - 当前 `main-web` 已承载平台治理原生页；
  - 新建子应用会引入新的壳层、路由和权限同步成本，不适合这个范围。

### 2. 复用现有用户列表接口，而不是新增“安全审核专用 API”

- 理由：
  - 当前 `UserVo` 已具备锁定相关字段；
  - 先用前端筛选即可形成工作台；
  - 可减少接口面扩张。

- 风险：
  - 用户量大时，纯前端筛选可能造成加载冗余。
- 当前权衡：
  - 先用现有接口收口能力；
  - 后续如果用户规模和运营频率证明存在性能压力，再独立出安全审核分页接口。

### 3. 审核动作先收敛为“解除锁定”

- 理由：
  - 后端已有稳定 `unlock` 语义；
  - 当前 `REVIEW_REQUIRED` 和 `LOCKED` 最终都可通过统一解锁动作恢复；
  - 对管理员来说，操作目标是“解除当前安全阻断”，不必强行区分多个前端动作名。

## 页面结构

建议在现有平台治理页中新增一个 `security-review` tab：

- 顶部摘要：
  - 待审核账号数
  - 永久锁定账号数
  - 最近审核时间提示
- 筛选区：
  - 锁定状态：`REVIEW_REQUIRED` / `LOCKED`
  - 关键字：用户名 / 显示名 / 邮箱
- 列表区：
  - 用户名
  - 显示名
  - 角色
  - 锁定状态
  - 锁定原因
  - 锁定时间
  - 最近审核时间
  - 操作按钮：`解除锁定`
- 抽屉 / 详情区：
  - 展示完整用户信息
  - 展示锁定审计摘要
  - 二次确认解锁

## 数据流

1. 页面进入平台治理后调用现有用户列表接口。
2. 前端把 `securityLockStatus !== "NONE"` 的记录收敛进安全审核视图。
3. 点击解锁后调用 `PATCH /api/users/:id/unlock`。
4. 成功后：
   - 刷新当前列表；
   - 更新摘要计数；
   - 给出成功提示。

## 组件拆分建议

- `PlatformSecurityReviewSection.vue`
  - 列表、筛选、摘要编排
- `PlatformSecurityReviewDetailDrawer.vue`
  - 用户详情与解锁确认
- `usePlatformSecurityReview.ts`
  - 拉取用户、筛选、计数、解锁动作

## 权限与审计

- 页面入口：继续复用平台治理域权限，至少要求 `user:read`
- 解锁动作：必须要求 `user:write`
- 不新增前端绕过逻辑；后端权限仍是最终裁决

## 测试策略

- 前端：
  - 安全审核 tab 正常渲染
  - 只显示 `REVIEW_REQUIRED` / `LOCKED`
  - 解锁按钮调用正确 API
  - 解锁成功后刷新列表与摘要
- 后端：
  - `UserVo` 映射包含 `securityLockStatus`、`securityLockReason`、`securityLockReviewedAt`
  - `unlock` 后返回状态恢复为 `NONE`
